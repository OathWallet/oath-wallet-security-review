# OW-2026-012 — Duplicate readback contradicts verified permission history

> Current audit target: [5.0.2 (104) prerelease](../review/RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

Severity: **informational**. A late, opposite callback to the permission
readback database API could overwrite a batch result while leaving its verified
history unchanged. The inconsistency is reproduced at the public API boundary.
A normal-app scheduling path that delivers such a duplicate has not been
established; the current status worker excludes concurrent checks for one send.
No signing bypass, secret disclosure, broadcast or fund loss was demonstrated.

## Root cause and possible presentation consequence

At regression-only commit `b7ff1f5eab70b244ba64a68da10addf3a4d8c4c4`,
`Packages/OathDatabase/Sources/OathDatabase/Permissions.swift:25–31` checks that
the send is confirmed, then conditionally updates a pending permission-removal
record. The following batch-state update and tracking-job deletion were
unconditional. A second callback cannot change the already completed history,
but could still replace the batch's result with the opposite value.

`OathAtmosphere/Permissions/OathPermissionsPage.swift` derives its removed-item
filter from the batch state and non-nil verification timestamp. Because that
timestamp comes from removal history, a contradictory batch could present a
previously verified active permission as removed until reconciliation. This is
a source-traced consequence, not a reproduced iOS display or attacker-controlled
provider exploit. The converse mismatch is also possible at the database API.

## Reproduction, fix and controls

`PermissionReadbackIdempotencyTests.swift` uses the production SQLite database,
real imported-key EVM signing and durable send journal with a public synthetic
key. It completes one readback, reopens the database, then submits the opposite
result. It checks history, batch state, verification timestamps, tracking-job
cleanup and another wallet's isolation without first running reconciliation.
The two directions fail on the baseline at exactly one assertion each: the
batch disagrees with the original verified result.

Fix `8f5c27c030fdd85e1d5c3c18d9da8aa92ac04c79` adds a `db.changesCount == 1`
guard at `Permissions.swift:29–31`, immediately after the conditional history
update and inside the same write transaction. Only the callback that transitions
the pending history may change the batch and tracking job. A duplicate leaves
all three unchanged. No migration, persisted identity, API or signing flow changes.

A control exercises actual reorganization triggers: move the confirmed
transaction back to pending, check that readback is pending with no timestamp,
confirm at a new height, and allow a fresh opposite result. Both directions pass
before and after the fix. Database restart is part of every case.

Three fresh, network-denied host processes run each of the three test methods:
**before: six expected failures and three passing reorganization controls;
after: all nine executions pass**. The identical test fixture is used in both
phases. Skips, crashes, missing tests and unrelated failures are rejected by the
evidence classifier. Tests run the production method rather than copied SQL.
