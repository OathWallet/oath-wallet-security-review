# OW-2026-018 — Namespace validation lost chain requirements and trapped on optional values

> Current audit target: [5.0.2 (104) prerelease](../review/RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

Severity: **low**, SDK availability and session-negotiation correctness. The
controlled tests demonstrate production SDK model defects, not a remote Oath
signing bypass, secret exposure or financial loss.

## Affected behavior

Regression-only baseline: `4fdb1653b925ff6c58af5c07cb256ee2e0897c79`.

- [Namespace.swift:64](https://github.com/devdasx/oath-wallet/blob/4fdb1653b925ff6c58af5c07cb256ee2e0897c79/Vendor/Reown/Sources/WalletConnectSign/Namespace.swift#L64) accepted malformed qualified keys, including empty references and extra components.
- [Namespace.swift:102](https://github.com/devdasx/oath-wallet/blob/4fdb1653b925ff6c58af5c07cb256ee2e0897c79/Vendor/Reown/Sources/WalletConnectSign/Namespace.swift#L102) force-unwrapped a parsed chain during approval. A malformed required key crashed this API. Its dictionary flattening could overwrite a qualified requirement when a base entry was visited later. It also rejected valid chain-qualified approval maps by expecting a base entry.
- [WCSession.swift:149](https://github.com/devdasx/oath-wallet/blob/4fdb1653b925ff6c58af5c07cb256ee2e0897c79/Vendor/Reown/Sources/WalletConnectSign/Types/Session/WCSession.swift#L149) force-unwrapped the optional chains array when updating a session with qualified requirements. Equivalent base-key updates were rejected, and updates with no required entries skipped account/key validation.
- [AutoNamespaces.build](https://github.com/devdasx/oath-wallet/blob/4fdb1653b925ff6c58af5c07cb256ee2e0897c79/Vendor/Reown/Sources/WalletConnectSign/Namespace.swift#L167) could reinterpret malformed qualified keys by taking their first/last components, require only one account among several required chains, or advertise optional chains without accounts.

The [namespace contract](https://specs.walletconnect.com/2.0/specs/clients/sign/namespaces)
allows chain-qualified entries and requires satisfaction of every required chain,
method and event. The repair checks those requirements at their chain scope; it
does not flatten permissions from unrelated chains together.

## Repair

Implementation: `2931f8d8f2e0f7dd3d737e2ee1aab32ba39683a4`.
[PR 26](https://github.com/devdasx/oath-wallet/pull/26) merged as
`c37dea5a5718e4dd27183c78a59856ff3de5653e`, with the same tested source tree.

The shared resolver rejects the tested malformed keys without force-unwrapping.
Approval checks each required chain against its corresponding base/qualified
session entries, considering only entries that contain an account on that chain.
Every required method and event must be present there. Dictionary order can no
longer erase a requirement. Valid qualified approvals remain supported.

Session updates use this shared validation before mutating namespaces or their
timestamp. Failure preserves the entire prior session. The builder validates
required keys, requires an account per required chain, omits malformed/unusable
optional entries and validates its final result. Existing signing, wallet
identities, encrypted storage and migrations are unchanged.

The existing rejection of a qualified proposal key that also supplies a separate
chains array is preserved. This finding does not claim complete protocol
conformance or exhaustive validation of the underlying CAIP parser.

## Reachability and limits

ApproveEngine validates required proposals before delivery and validates approval
namespaces before settlement. Oath calls AutoNamespaces through its own supported
method/network policy and selects accounts by exact selected chain identifiers.
Those app checks can reject malformed/unsupported input before a later SDK trap;
a complete remote peer-to-Oath crash was not demonstrated by this host corpus.

Incoming session updates require the peer to be controller. Ordinary Oath-approved
sessions make the wallet the controller. The controller response path instead
applies the stored outgoing update; no direct Oath update caller was found in the
inspected service. Tests therefore prove the SDK API defect without assuming
all integrations expose it identically.

Permission omission is not extra signing authority: it can establish an
incomplete session, but no unauthorized signature was demonstrated. Parser edge
cases, session replay/lifecycle behavior and the broader dependencies remain
under review. No simulator, physical device, live relay, financial transaction
or App Store operation occurred.
