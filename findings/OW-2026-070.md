# OW-2026-070 — Sui transaction parser traps on nonzero-origin Data

Severity: **Low, public API robustness / availability.**
Status: **Fixed and retested in source; hosted replay pending.**

At `b3f1f6af98bedfe850d390cac684a563c598e3ac`,
`Packages/OathAnkr/Sources/OathAnkr/WalletConnectSui.swift:90–93` passes the
caller's `Data` directly to a reader whose offsets start at zero. Foundation
`Data.SubSequence` is also `Data`, but a slice can retain a nonzero `startIndex`.
`SuiConnectBCS.take` applies a zero-origin range to that slice. The bounds check
against `bytes.count` does not make that range valid. The publish/upgrade command
also indexes the outer `bytes` with the reader's offset.

The production-parser reproduction builds an ordinary synthetic transaction
using `SuiSendPlan.transactionBytes`. Its zero-origin control passes. Wrapping
the bytes with a prefix and removing the prefix produces the same byte contents
but terminates the test process with SIGTRAP (exit -5). A separately isolated
test for truncated slices also terminates with SIGTRAP instead of throwing.

The normal WalletConnect RPC initializer decodes base64 into fresh, zero-origin
`Data`; no remotely triggerable app exploit is established. This finding is an
internal/public parser contract failure, not a signing bypass or fund-loss claim.

Repair `018cd8316d5f2c899f5ccbd3bc8547b3f7a7bea0` rebases the bounded input once
with `Data(bytes)` before any reader or outer-buffer indexing. The serialized
contents, limits, address checks and transaction signature are unchanged. It
does not alter stored records, wallet identities or a persistence format.

The identical three-method fixture passes after repair. It checks four nonzero
origins against the ordinary-buffer control and rejects every truncated prefix.
The original two process crashes remain preserved as before evidence.
