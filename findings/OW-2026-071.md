# OW-2026-071 — XDR and SCALE readers trap on nonzero-origin Data

Severity: **Low, parser availability / robustness.**
Status: **Fixed and retested in source; hosted replay pending.**

At `018cd8316d5f2c899f5ccbd3bc8547b3f7a7bea0`, the reader in
`Packages/OathAnkr/Sources/OathAnkr/StellarSendXDR.swift:91–96` and
`Packages/OathAnkr/Sources/OathAnkr/PolkadotScale.swift:3–9` retains the caller's
`Data` while using zero-based offsets for `subdata(in:)`. Foundation slices can
retain a nonzero `startIndex`; checking the remaining byte count does not make
those indexes valid. The XDR vector/map discriminator also indexes the stored
buffer directly using its relative offset.

The nine-method fixture invokes production implementations with synthetic
inputs. Three ordinary-buffer controls pass before the repair. Six separate
processes terminate with SIGTRAP (exit -5): Stellar public plan validation and
signing with sliced Soroban resources, truncated resources, XDR vectors/maps,
SCALE compact values, truncated compact values, and minimal runtime metadata.

The Stellar reproduction reaches the public `StellarSendPlan` constructor and
`validate` entry point. SCALE reader and metadata construction are internal and
are exercised through the test module. Current provider decoders create fresh
zero-origin buffers. No remotely triggerable app exploit, signing bypass or
fund loss is demonstrated by this fixture.

Repair `2f914715224db31e91f1ce1f0dea4c236c043920` normalizes input once in each
reader initializer with `Data(data)`. This makes both the reader operations and
XDR's direct discriminator access use one consistent origin. It changes no
bytes, wire format, wallet identity, stored record, or authorization rule.

All nine methods pass after the repair. Valid sliced buffers at four different
origins produce the same transaction bytes or decoded result as the controls;
truncated buffers throw rather than trap. The before failures remain retained.
