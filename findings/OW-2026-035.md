# OW-2026-035 — A private extended-key import accepted public point data

**Impact and precondition.** A checksummed extended private key could contain a compressed public point in its key-data field. The wallet interpreted the public X coordinate as a private scalar. A party who knows the malformed encoding can reproduce this unexpected wallet and its spend keys. This requires an incorrectly encoded or deliberately crafted import. It does not recover the private key corresponding to the original public point. Ordinary correctly encoded private imports and generated wallets are outside the demonstrated failure. Severity: moderate wallet-import integrity, with conditional loss if the user funds an address derived from public data.

## Evidence

BIP32 serializes an extended node using 78 bytes before the checksum. Byte 45 must be zero for a private version; a compressed public key starts with 02 or 03. The version, checksum and scalar range cannot substitute for that check. [Serialization and invalid vectors](https://bips.dev/32/#serialization-format).

The [test-only baseline](https://github.com/devdasx/oath-wallet/tree/7a737d938422d2a6d50ae3143bbca27bd95a87c2) used a synthetic version header, valid checksum, fixed chain code and the public secp256k1 generator point. All four networks returned the public X coordinate as the imported scalar. A fifth case reproduced acceptance under an alternate private version. The valid-private and explicit-public controls passed. The first-party normalization functions checked the version then passed the payload to BDK. In its selected Rust implementation, Xpriv::decode takes the scalar from bytes 46 through 77 and omits byte 45. The secp256k1 scalar check operates only on the 32 bytes it receives.

The fix checks the original marker before any version alias is normalized. The app import boundary surfaces its existing invalid-key result. For already saved wallets a separate recovery function requires the scalar stored beside the text, verifies its length and equality, canonicalizes only the marker, then validates the network, private version and supported node scope through the normal strict parser. It preserves the chain code and derived branches. Genuine public-version inputs and mismatched stored scalars fail. **Someone who previously funded a wallet imported from a malformed, shared or public-derived key should move the funds to a newly generated wallet.** Correcting the serialization cannot make an already known scalar private.
