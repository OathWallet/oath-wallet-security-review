# OW-2026-063 — Wallet removal races a new signed transaction journal

Severity: **Low, recovery and retention correctness.** The test demonstrates
loss of a pending local recovery record during an authorized removal. It does
not demonstrate unauthorized signing, key disclosure, broadcasting or lost funds.

## Source and trigger

The vault's removal operation checks pending transactions, then separately
persists encrypted membership and reconciles SQLite. A signed transaction can
enter its journal after that check while the wallet is still active in SQLite.
Both operations can succeed. Recovery queries subsequently omit the removed
wallet, and retention cleanup eventually cascades its pending journal away.

This was reproduced after OW-2026-062's preflight repair, at application
`0e91ce56f91ef56b3e45629967e01e449be0052f`. The test-only revision is
`82ea45249ae40e5ab0be39d671fbfc96b6e43069`. The selected vault removal,
reconciliation and XRP signing bodies are identical at the build 103 baseline;
the source-binding record preserves hashes and line ranges.

At the reproduction revision, the affected sequence is in
`OathAtmosphere/Wallet/OathWalletVault.swift:2336–2369`;
reconciliation is at lines 2243–2283 and XRP signing at 822–839.
`Packages/OathDatabase/Sources/OathDatabase/WalletConnectXrplJournal.swift:46–78`
contains the pending query and journal write. The Connect service calls signing
then journaling around `OathWalletConnectService.swift:1200–1206` and resumes
pending work around lines 2282–2337. These are scoped traces, not a complete
review of the large vault or Connect service files.

## Reproduction

The fixture creates two wallets with public synthetic imported XRP keys and
uses the production vault signer, request verifier, encrypted envelope and
database journal. An in-memory storage implementation pauses its `vault-v1`
update after pending-work validation and before the encrypted write. While it
is held, the fixture calls the real journal API with the previously authorized
signed transaction, then releases the write. No production function is modified
to make this ordering possible.

The unchanged 23-case fixture produces **19 passes and four failures** before
repair. Both operations succeed, the row disappears from ordinary and reopened
recovery queries, and retention purges it. Controls cover journal-first,
removal-first and rejected encrypted writes, including retry after write failure.
Readiness has a bounded explicit gate; a missing gate fails the test rather than
pretending the desired ordering occurred.

## Repair

Pending validation and a durable wallet-removal reservation now share one SQLite
writer transaction. Insert/update guards fence pending ordinary sends and all
seven Connect journal tables while the encrypted write and lifecycle replay run.
Whichever writer wins first prevents the conflicting operation.

Reservation cleanup is bound to a captured token. A failed encrypted write
releases that operation's token through local cleanup independent of task
cancellation. A failed cleanup remains fenced until authenticated recovery.
After interruption, replay follows the persisted encrypted membership before
releasing captured reservations. Unlock holds the existing mutation guard so
stale concurrent reconciliation cannot prematurely release a removal fence.

Migration `v106_wallet_removal_reservations` adds the table and guards without
rewriting shipped migrations. Wallet deletion cascades its reservation; explicit
reset still erases the ledger. Legacy already-removed cleanup remains supported.
No network behavior, wallet secret format or authentication policy is changed.

## Limits and evidence

The new runtime experiment exercises XRP journaling, not seven complete chain
signers or a live dApp/UI. A separate schema matrix covers the eight tables'
pending insert/update guards. Recovery tests use synthetic credential stores,
not Apple's Keychain or Face ID. Other signing-only authorization interleavings
remain separate review work. The whole-wallet audit is incomplete.

The original tagged app is not retroactively repaired; a source repair does not
prove App Store delivery. No App Store, simulator, physical-device or live-ledger
operation is part of this checkpoint.
