# OW-2026-072 — malformed Stellar plan timestamps trap during validation

Severity: **Low, saved-data / public API robustness.**
Status: **Fixed and locally retested; hosted replay pending.**

At `152e094f85f196479d2ab08856eaf3b0264cd6c1`,
`Packages/OathAnkr/Sources/OathAnkr/StellarSendPlan.swift:67` converts a
caller-controlled `Date` interval to `UInt64` with a trapping initializer.
The normal age check rejects implausible dates, but reconciliation deliberately
uses `validate(checkAge: false)` so it can verify old, already-signed sends.
An infinite or finite out-of-range timestamp therefore reaches the conversion.

The production verifier `StellarSendCrypto.verify` invokes that structural
validation. `StellarSend.swift` decodes saved JSON plans, and
`SendReconciliation.swift:30–40` routes them into the verifier before submitting
or checking status. A synthetic JSON-decoded plan with `createdAt = 1e30`
crashes the verifier instead of throwing. Two other isolated cases reproduce
the same trap with direct finite/infinite dates. Ordinary saved-plan,
NaN-rejection and expiry-boundary controls pass before the repair.

This demonstrates three process crashes, not a remote exploit. Normal quote
creation supplies the local current time; no attacker-controlled persistence
writer, signature bypass or funds loss is demonstrated. An already-corrupted
saved plan is a relevant recovery boundary, but no physical-device crash is
claimed.

Repair `814596f8bb25a2c32ea25bba1fb036aee3303ca6` checks finiteness and uses
`UInt64(exactly:)` after explicit whole-second truncation. The original age,
deadline, fee, amount, signature and network checks remain. Invalid structural
dates throw `StellarSendError.malformed`; valid old plans remain verifiable.
No persisted format or wallet identifier changes.

The identical six methods change from three passes/three SIGTRAPs to six
passes using fresh, separate build directories. A valid JSON round trip
retains the unsigned transaction bytes and validates the original signature.
Tests include fractional seconds, the existing near-epoch behavior, the
180-second lifetime cap and the -5/90-second age boundaries.

The first fixture compile error and a discarded stale-executable retest are
preserved and explicitly excluded from the successful repair evidence.
