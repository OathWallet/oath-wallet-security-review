# OW-2026-060 — Valid large issued-token amounts fail XRP transfer-rate calculation

> Current audit target: [5.0.2 (104) prerelease](../review/RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

Severity: **Low, payment availability/correctness.** No incorrect signed payment,
key exposure, authorization bypass or loss of funds was demonstrated.

## Affected source and trigger

`Packages/OathAnkr/Sources/OathAnkr/XrplSendAmount.swift`, the `ratio` function,
at baseline `c7acd23bb139864a40273f405d18b479589d2b20` and pre-fix commit
`a904515793b087289140e4411924f030b3fe61ff`. `XrplSendClient.prepare` calls this
function at lines 228 and 236 to calculate available token balance and debit.

The internal representation uses 96 decimal places. The protocol-valid issued
amount `1e90` is therefore the integer `1` followed by 186 zeros. Applying a
1,000,000,000 / 1,000,000,000 transfer rate must return the same value. Instead,
the original helper throws `amount`.

Long division emits one quotient digit for each digit of the multiplied
numerator, including leading zeros. `canonical` rejects strings longer than 193
characters before stripping zeros. The padded intermediate buffer crosses that
limit even when the actual quotient remains within it. This can prevent quoting
a mathematically valid large issued-token payment, including a 1:1 rate.

The [XRPL amount format](https://xrpl.org/docs/references/protocol/data-types/currency-formats)
allows the example above; the [binary specification](https://xrpl.org/docs/references/protocol/binary-format)
defines the bounded mantissa/exponent representation. These references establish
the numeric domain, not a live transaction result. No node was contacted.

## Reproduction and repair

The exact same **4,900 deterministic cases** exercise unmodified production
amount functions and their real integer-arithmetic dependencies, compared with
Python arbitrary-precision integer/decimal calculations. The pre-fix run records
**4,843 passes and 57 failures**, all transfer-rate cases. Four failures use the
explicit protocol-valid `1e90` example at 1:1 and 2:1 rates in both rounding modes.
Random cases also test the helper's wider bounded integer domain; those are not
all representable ledger token amounts.

Public repair [PR #74](https://github.com/devdasx/oath-wallet/pull/74),
commit `6783750661c43d3511d8973a2de77106fdf2001d`, removes leading padding before
validating the quotient and validates the rounded result as well. All 4,900
identical cases pass. A package regression additionally covers large valid
amounts, sub-unit rounding and an oversized true quotient. The change preserves
the input bound, transfer-rate bounds and rounding direction.

The host property check does not execute the signing engine, transaction
serialization, full quote transport, UI or live ledger. Source tracing establishes
the quote call path. Package tests and build receipts are recorded separately.

No App Store delivery is claimed. The historical baseline retains the defect;
the public source repair and its final validation are tracked in the checkpoint
evidence.
