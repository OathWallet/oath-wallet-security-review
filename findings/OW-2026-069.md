# OW-2026-069 — History restarts omit the ticket-to-account binding

Status: **Fixed and retested in source; hosted replay pending.**
Severity: **Low, internal database boundary.** No application-level exploit is demonstrated.

At `05e7917f0a3c26072b1a6b88d2e9e4a0d0310427`, the restart methods in
`Packages/OathDatabase/Sources/OathDatabase/SuiLedger.swift:118–124` and
`Packages/OathDatabase/Sources/OathDatabase/XrplLedger.swift:117–123`
validate a sync ticket and separately load a cursor by the caller-supplied
account ID. They do not require those two account IDs to match. A valid ticket
for account A can therefore restart the saved cursor of account B.

Two production-database host tests create separate synthetic wallets/accounts,
commit a history page for B, and pass B's cursor with A's valid ticket. Both
methods wrongly mutate B's cursor before the repair. The ordinary Sui/XRP
synchronizers obtain their cursor using the same ticket; this review has not
shown a remote caller reaching the mismatch through the app. The finding is
an unenforced database contract, not proof of another user's wallet access.

Repair `b3f1f6af98bedfe850d390cac684a563c598e3ac` requires
`cursor.accountID == ticket.account.id` alongside the existing generation and
saved-cursor equality checks. Both mismatched calls now throw `StoreError.staleSync`
and leave B's cursor unchanged. No history records, transaction bytes or balance
values are changed by rejection.

[Paired results and adjacent regression checks](../review/HISTORY-RESTART-BOUNDARIES.md).
Tests use real SQLite and synthetic local records with runtime networking denied.
