# OW-2026-061 — XRP Connect accepts inconsistent simulation metadata

Severity: **Low, defensive preflight correctness.** No unauthorized signature,
incorrect signed transaction, key exposure or loss of funds was demonstrated.

## Affected source and trigger

`Packages/OathAnkr/Sources/OathAnkr/XrplSendClient.swift:580–584`,
`walletConnectCheck`, at baseline
`c7acd23bb139864a40273f405d18b479589d2b20` and reproduction commit
`f8a6d29803594f1f3a74063e92f90b8155122556`.

The helper checked only the top-level simulation `engine_result`. It accepted
`tesSUCCESS` even if `meta.TransactionResult` was `tecPATH_DRY`, null, missing
from an empty object, or the wrong JSON type. Both `walletConnectReview` and
`walletConnectPreflight` shared that guard. Ordinary XRP sends already required
success in both fields.

The [XRPL simulate specification](https://xrpl.org/docs/references/http-websocket-apis/public-api-methods/transaction-methods/simulate)
documents metadata in successful non-binary responses. Simulations do not
guarantee the result of a later submission because ledger state can change.
This finding concerns internally inconsistent or incomplete responses from a
provider, not a claim that an honest node emits these fixtures.

Source tracing in `OathAtmosphere/Scanner/OathWalletConnectService.swift`
connects review to request preparation (lines 2340–2390), and preflight to the
fresh authorization/signing path (lines 1183–1213). Previously signed journal
retries are a separate path. These limited source traces are not a complete
review or runtime test of the UI service.

## Reproduction, repair and limits

Four synthetic metadata variants through each of the two production methods
produce **eight failed assertions in two methods** before the fix. Four control
methods pass. These are real OathAnkr package calls with a mock RPC transport;
the new cases assert zero submit calls. No wallet secret or live node is used.

[PR #75](https://github.com/devdasx/oath-wallet/pull/75),
commit `8a31eb265c34ef7f37ba21741201842366d43b7b` requires both fields to report
`tesSUCCESS`. Failure codes still pass through the existing safe-code filter;
unknown or malformed values become `UNKNOWN`. The unchanged six tests pass
afterward, including valid response and `DeliverMax` alias controls. The
broader XRP package run passes 43 methods and explicitly skips four live tests.

A provider that fabricates both success fields is outside this defense. No
trustless ledger verification, live transaction outcome or UI behavior is
established by these tests. The fix prevents these malformed responses from
passing the review/preflight prerequisite; it does not claim proven fund loss
in the original implementation.

The original baseline remains affected. Public-source repair is distinct from
App Store availability, which has not been verified or changed in this review.
