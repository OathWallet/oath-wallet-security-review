# OW-2026-064 — Removed wallets retain suspended signing authority

Status: **Fixed in public source and locally retested; hosted replay pending.**

Severity: **Medium, stale authorization.** A previously authorized signing
operation can finish after its wallet is removed, including permanent removal.
The test proves a valid signature at the vault boundary, not delivery through a
WalletConnect relay, a broadcast, unauthorized initial consent or loss of funds.

## Source and reproduction

Baseline: `0b1b4aeabf01d03bc417f00d4eb022a5bb0c049d`, version 5.0.2 (104).
`OathAtmosphere/Wallet/OathWalletVault.swift` signs messages at lines 1077–1098
and typed data at 1102–1122. These paths retain decrypted contents across an
awaited database account lookup. Their generation check at line 1847 detects
lock/reset, but wallet removal at lines 2355–2405 does not invalidate it.
The batch permission authorization also survives removal of its wallet.

The fixture pauses the actual GRDB account SELECT after authentication, completes
an authorized removal on another connection, then resumes the account read.
It uses public synthetic imported EVM keys, the production encrypted envelope,
database and EIP-191/EIP-712 signing implementations. Credential storage and
biometrics are in-memory adapters. Network access is denied during execution.

The final 66-case baseline fixture reports **54 passes and 12 failures**: message
and typed-data signatures survive soft removal, permanent removal and
remove-then-restore; existing batch consent survives the same six scenarios.
Controls cover lock, another wallet's removal, a rejected encrypted save and
fresh authorization after restoration. The account-read gate is bounded and
must actually be reached; its timeout cannot count as success.

## Repair

All 26 vault signing entry points capture a wallet-scoped removal generation in
addition to the existing global authentication generation. A successful encrypted
removal changes that wallet's generation before the next suspension and clears
its permission grant. A failed save and removal of another wallet preserve
existing authorization. Restoration permits a new request, never resumes the
pre-removal request. Lock invalidates the global generation as before.

Initial repair `5b03abd86443a72947ff4fcdda4f94b348620627` passed all 66 focused
cases and unsigned iOS Release compilation. Broader host regressions found an
error-contract regression: an initially invalid wallet returned cancellation
instead of the existing locked error. Follow-up
`1c5a9fab7562dab4583810365ab6b4a2e248d6a1` preserves that error contract while
retaining cancellation for requests invalidated by removal. It fixed the WalletConnect error but ordinary sends require their own chain-specific changed error. Final repair `0614556b993f85808b13e3a69984ce36050a8dfe` leaves those existing membership checks in place and adds only removal-generation validation; its full selected regression run passes (616 assertions across 15 suites). Earlier failed attempts and results are retained separately.

## Limits and remaining work

The runtime fixture covers EVM messages and typed data, not every chain's
removal interleaving. Broader existing signing tests check other chain paths.
The session service has additional membership checks before relay responses;
this experiment does not bypass or exercise them. Apple's Keychain, Face ID,
UI, simulator, devices and live networks were not used. The new pending-permission experiment below covers one additional authorization
interleaving, not every permission-service path. No persisted wallet format or
network behavior is changed. The whole-application review remains incomplete.

Reproduction: `scripts/connect-removal-read.py`, fixture
`fixtures/connect-removal-read/Checks.swift`. [Validation manifest](../evidence/5.0.2-build104/connect-removal-read/validation/manifest.json) and [review scope](../review/CONNECT-REMOVAL-READ.md) preserve the exact tested source, attempts and results.

## Pending permission approval extension

A separate 14-case experiment holds the synthetic biometric response while an
authorized removal and restoration completes. At `1c5a9fab7562dab4583810365ab6b4a2e248d6a1`,
13 checks pass and one fails: the old approval creates a fresh batch grant after
restoration. Soft/permanent removal, lock, unrelated removal and rejected saves
behave as expected. The repair extends the same removal generation to approval
issuance. The fixture is `fixtures/connect-removal-read/PendingConsent.swift`;
its first compile failure (await inside a Boolean autoclosure) is retained as a
test-writing failure, separate from the reproduced application behavior.
