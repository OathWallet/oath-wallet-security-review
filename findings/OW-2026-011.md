# OW-2026-011 — Consumed permission grants survive revocation during preparation

> Current audit target: [5.0.2 (104) prerelease](../review/RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

Severity: **low**. A previously approved, removal-only operation could still
produce a signature after its batch grant was ended, replaced or expired while
the signing invocation awaited preparation. No arbitrary-transfer authorization,
cross-wallet signature, secret disclosure or live fund loss was demonstrated.

## Root cause and boundary

At regression baseline `976971f0ca3362cfba8c63bc738bd80d15abf096`,
`OathAtmosphere/Wallet/OathWalletVault.swift` consumes a permission scope at the
start of `signTronSend` (650–683), `signSolanaSend` (1008–1044) and
`signEVMSend` (1153–1186). Scope consumption is single-use and binds the wallet,
account, network, owner, removal operation and maximum fee. After consumption,
the invocation awaits preparation and database reads before signing.

Those paths recheck `authenticationGeneration`, which correctly rejects locking
and cancellation. However, `endPermissionBatch`, replacement authorization and
the 30-minute grant deadline do not change that generation. The signers did not
recheck the current grant before signing. The executor's check before starting
an item cannot revoke an already-running signing call.

The reachable app path is batch review → coordinator → permission service →
existing chain send service → vault signer. This is a capability-lifetime defect
for an already reviewed removal, not a grant of general signing authority. The
expiry fixture advances the grant clock only; it does not assert that a real
30-minute-old transaction quote would remain valid on every chain.

## Same-fixture reproduction

`Tools/CheckPermissionBatchRaces.swift` creates a fresh synthetic imported-key
wallet, local SQL database and queued permission-removal plan for each scenario.
It parks cancellation-resistant preparation, confirms the original scope was
consumed by rejecting a duplicate request, changes grant state, then releases
preparation. Returned signatures are checked by the production chain verifier.

Each process runs 21 scenarios and 84 assertions across EVM (Arbitrum), TRON and
Solana: valid, unrelated end, matching end, replacement grant, expiry, lock and
cancellation. The first two must sign; the remaining five must reject. No
signed-byte journal write is made by this signer-only harness.

Before: three network-denied executions each report exactly nine failed
assertions—end, replace and expire on each chain—and 75 passing controls.
Total: **27 expected failures, 225 passing assertions**. The runner rejects
unrelated errors, crashes, missing summaries and incomplete counts.

Fix `da7a88ad0b3dd7cc56304d2e84e9b8b134c7eb4b` checks the same grant's identity,
deadline and unlocked state immediately before synchronous signing and again
before returning signed bytes (helper 420–424; calls 686/689, 1049/1052,
1193/1196). No suspension occurs between the first check and signing. The
post-sign check also covers deadline passage during signing. Scope consumption,
fee ceilings, PIN authorization, normal sends and database formats stay intact.

After: the same three executions pass **all 252 assertions**. Both test fixture
hashes match before and after; binary hashes differ. The controllable monotonic
clock was introduced before the failing baseline and defaults to the real
`ContinuousClock` in production. Its baseline commit also selects the actual
imported-key EVM/TRON/Solana adapters in the host harness.

## Reproduce and limitations

```sh
python3 scripts/checkout.py
git -C .work/source worktree add --detach ../batch-race-before 976971f0ca3362cfba8c63bc738bd80d15abf096
python3 scripts/permission-batch-races.py .work/batch-race-before --before --output .work/batch-before --scratch .work/batch-before-build
python3 scripts/permission-batch-races.py .work/source --output .work/batch-after --scratch .work/batch-after-build
```

Evidence: [`evidence/permission-batch-races`](../evidence/permission-batch-races).
The initial fixture attempt selected incomplete TRON/Solana host adapters; it
failed with a malformed-plan error and is not counted as a reproduced finding.
A later build failed because cached Clang modules used a different `/var` versus
`/private/var` path. That failed attempt remains visible; the authoritative
before/after runs use one fresh canonical scratch path. A wrong-source-pin
preflight was rejected before testing and does not count as execution evidence.

These are macOS host checks using production vault/SQL/imported-key signing and
verification with synthetic credentials; real biometrics and HD derivation are
substituted. No UI, simulator, physical device, broadcast, production account or
App Store operation is included. Revocation after bytes have already returned
and entered the durable send journal is outside this fix's boundary. The full
wallet and dependency audit remains incomplete.

Published in [application PR 15](https://github.com/devdasx/oath-wallet/pull/15). Merge `00e803665a6b030ed1c035939866e739b2196d57`
has the same source tree as the tested fix: `25b706f9c136e26c850c1204fee974f33b57b5dd`.
Source-tree equality does not establish installed App Store binary equivalence.
