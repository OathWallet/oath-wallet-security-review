# OW-2026-066 — NEAR refresh completes with stale sent-token balances

Status: **Fixed in public source and retested locally. Hosted replay pending.**

Severity: **Low, balance freshness and retry completion.** After a NEAR send,
an account refresh can succeed while an individual token contract read fails.
The wallet retains the last known token balance, but the post-send refresh
predicate incorrectly declares that balance current and ends its durable retries.
A newly observed snapshot from a block before execution is also accepted.
No unauthorized signing, key exposure or fund loss is demonstrated.

## Cause and reachable path

At `5d91d1e4dfd36c56031c7a8fb1ee305446dc54de`,
`Packages/OathDatabase/Sources/OathDatabase/NearSend.swift:14–23` checks only
the account-level `nearSync.observedAt` and failure field, plus transaction
presence. `commitNearInventory` deliberately preserves the old token amount,
timestamp and height on an individual contract-read failure while updating the
account-level observation. That preservation is correct; treating it as a
successful balance refresh is not.

`OathAtmosphere/Send/OathPostSendBalanceRefresh.swift` calls the predicate and
returns accepted send IDs to the production durable refresh worker. That worker
marks accepted jobs complete. Thus this condition can stop the retry path even
though the sent token still shows its pre-send amount. Beginning another sync
or reopening SQLite does not itself repair the missing token observation.

## Reproduction and repair

The synthetic fixture uses production SQLite APIs, validated native/token send
plans, actual Ed25519 signatures, receipt settlement and history commits. Four
of six methods fail before the repair. The failed-token case separately asserts
that the original amount and observation timestamp were retained. Positive
controls include a successful zero balance and a successful read at the execution
block. No real provider or transaction is used; runtime networking is denied.

Commit `fd06fdff104d128e00cc414d2de1472f11752e04` requires successful non-null
observations of the sent asset and the native fee asset, with timestamps and
block heights at or after execution. Failed or missing observations keep the
job pending. The exact same six methods pass afterward, including recovery
following a failed read and a database reopen.

The repair changes no stored identifiers, schema, amount, signed bytes,
transaction result, authorization, or cached-balance preservation behavior.
Existing databases require no migration.
