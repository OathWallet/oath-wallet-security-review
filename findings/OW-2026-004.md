# OW-2026-004 — plaintext accepted at encrypted WalletConnect relay ingress

> Current audit target: [5.0.2 (104) prerelease](../review/RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

Severity: **medium, protocol message integrity**. Fixed in source commit
`f506dd8b820476296a6348c0ccbbdc42164c21f5`; App Store availability is not established.

Affected baseline: 4.1.15 (100),
`c7cdbde5e9f136b595500e92fbc904b107dcd8ee`. The same ingress implementation
remained in `f23413c848d202c2b3c7061bdb349e07144ab0a2`.

## Cause and consequence

`Vendor/Reown/Sources/WalletConnectNetworking/NetworkingInteractor.swift:329`
passed relay messages directly to the general serializer.
`Vendor/Reown/Sources/WalletConnectKMS/Serialiser/Serializer.swift:99` accepts
type-2 envelopes by decoding plaintext JSON, without a topic key or an
authentication tag. Type 2 is also used by the separate Link Mode dispatcher;
support there is not justification for accepting it on the encrypted relay path.

An entity able to deliver a relay subscription frame for a known topic can
therefore place an unauthenticated protocol request into `requestPublisher`.
This violates the encrypted relay's message-authentication boundary even when
the receiver already has the correct topic key. It does not require the sender
to know that key. The production `SessionEngine` subscribes to those requests;
its delete handler checks that a session exists and relies on transport
authentication rather than requesting signing authorization.

The demonstrated result is **request dispatch**, with a synthetic
`wc_sessionDelete` message. The test does not instantiate the complete session
engine, delete a real session, sign a transaction, steal funds, or establish an
arbitrary website's ability to publish into another client's relay subscription.
A malicious/compromised relay is within the tested transport threat model.
App-level signing authorization remains a separate boundary. These limitations
are why this is not reported as a demonstrated signing or fund-loss bypass.

## Reproduction and fix

The four regression cases in
`Tools/WalletConnectSDKValidation/RelayEnvelopeAuthenticationTests.swift` use the
production `RelayClient`, `NetworkingInteractor`, serializer and cryptography.
Only the relay dispatcher and key-value store are synthetic/in-memory. No live
relay, personal credentials, wallet database, simulator or device is involved.

- Plaintext injected while the receiver has a topic key: rejected after repair.
- Plaintext injected without any receiver topic key: rejected after repair.
- Correct encrypted type-0 request: dispatched; a flipped authentication tag is rejected.
- Correct encrypted type-1 key-agreement envelope: dispatched.

With only the production ingress file restored from the original baseline,
**two rejection tests fail and two positive-control tests pass**. With the
repair, **all four pass**. The repair permits only encrypted envelope types 0
and 1 at relay ingress. The general serializer and Link Mode are unchanged.

Reproduce from a clean checkout of the audit's pinned application source:

```sh
python3 scripts/relay-envelope-check.py /path/to/oath-wallet --output /tmp/relay-evidence
```

The runner verifies the original file hash and exact final source revision,
copies the required SDK inputs into a temporary directory, uses the same test
corpus before/after, asserts exact per-case outcomes, records durations and
source/test/log hashes, and leaves the checkout unchanged. The before tree is
explicitly a constructed reproduction, not a claimed clean final build.

The full SDK host suite also passes **23 cases, with one intentional skip**.
That skipped diagnostic-reporter isolation case passes in its own process.
Local reproduction evidence and final-source checks are recorded under
`evidence/relay-envelope/`; broader audit completion remains outstanding.
