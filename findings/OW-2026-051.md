# OW-2026-051 · A replacement symlink could redirect a backup read

The release first checked a URL's cached resource values and subsequently opened its path with a separate file handle. An atomic replacement of the last directory entry could redirect that open after the regular-file check succeeded. The [release code](https://github.com/devdasx/oath-wallet/blob/c7acd23bb139864a40273f405d18b479589d2b20/Packages/OathCloudBackup/Sources/OathCloudBackup/CloudRestore.swift#L113-L143) runs inside file coordination, but another writer need not participate in that coordination.

The first synthetic test prefetched metadata for a regular backup file, replaced its directory entry with a symlink and called the production bounded reader. It returned the contents of a different file. A second test used atomic directory-entry swaps while invoking the coordinated restore reader itself. That reader also returned the unrelated sentinel. All files were temporary and the sentinel was outside the synthetic backup directory. No real credentials, arbitrary remote access, authenticated decryption or wallet import were demonstrated. The file must be readable by the process. Severity is low for this local file-selection boundary.

[PR 63](https://github.com/devdasx/oath-wallet/pull/63) opens the final entry without following symlinks, checks the regular-file type and size with the open descriptor, and reads through that descriptor. Nonblocking open prevents a named pipe from hanging the reader. The read limit still applies to a file that grows after validation. This fix covers final-entry substitution. It makes no new claim about replacement of ancestor directories or behavior of a live iCloud account.

The source repair was merged after passing the complete [backup package tests](../evidence/5.0.1-build103/backup-file-identity/read/OathCloudBackup.json) and an unsigned generic iOS Release build.
