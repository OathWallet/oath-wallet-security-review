# OW-2026-015 — Optional transaction metadata outside the encrypted relay payload

Severity: **low**, a privacy/minimization defect. A relay operator could receive
method names, chain identifiers, transaction hashes and contract addresses as
separate `irn_publish` parameters despite Oath disabling SDK event telemetry.
This does not expose private keys or recovery phrases, bypass authorization,
modify a signed transaction or demonstrate financial loss. Transport TLS still
protects the network connection; the issue is visibility to the relay rather
than to the intended end-to-end-encrypted peer alone.

## Reachable source and root cause

Regression-only source: `0c466ea73d0875bdb46ce37a9bfcf6c702ee3639`.
The unchanged production behavior also exists at the prior reviewed application
`f9cccef32d4508fca13ddbf52d3eb882b5d8f0f1`.

- `OathWalletConnectService.configure` disables `Events.instance` telemetry.
- `SessionResponder.respondSessionRequest` independently calls `TVFCollector`
  with the approved request and its result. This collector does not consult the
  Events telemetry setting.
- `NetworkingInteractor.respond` encrypts the peer response and separately passes
  `tvfData` into `RelayClient.publish`.
- `Publish.Params` stored `rpcMethods`, `chainId`, `txHashes` and
  `contractAddresses`; synthesized Codable encoding emitted any non-nil values
  beside `message`. A relay therefore did not need the peer session key to read
  these optional fields. Transaction hashes can link a relay session with public
  on-chain activity. Existing routing identifiers already permit other forms of
  traffic correlation, which this repair does not eliminate.

The request-side `SessionRequester` has the same optional collector path. The
outbound encoding boundary covers both callers and any reconstructed Params.
The current [WalletConnect relay specification](https://specs.walletconnect.com/2.0/specs/servers/relay/relay-server-rpc#publish)
shows publish routing and message fields without requiring these TVF additions.
That source comparison supports omission; it is not a live service acceptance test.

## Repair

Implementation and tested source: `e7aed8c9d08357df10a4f85be7d069a66fad07f8`.
`Vendor/Reown/Sources/WalletConnectRelay/RPC/Methods/Publish.swift` now uses an
explicit outbound encoder allowing topic, encrypted message, TTL, prompt, tag
and correlation ID. The four optional transaction metadata properties cannot
appear in outgoing JSON, including after decoding an older Params object.
Decoding remains compatible, and the peer payload and routing values are intact.
No stored wallet migration, signing, chain broadcast or transaction amount code
changed. This policy is enforced at the final encoder rather than relying only
on a particular caller supplying nil.

## Before/after reproduction

The identical four-case Swift fixture exercises production Publish, TVFCollector,
Serializer and QueuedSerializer implementations with public synthetic inputs:

1. An explicitly populated metadata object must not emit four optional fields.
2. The real EVM response collector must not bypass that encoder boundary.
3. Decoded parameters containing old metadata must not republish it.
4. A genuine locally encrypted response must preserve routing fields and decrypt
   to the exact peer response. This control passes before and after.

Before: **11 expected assertions across three failed tests**, plus **one passing
control**. After: **all four tests pass**. The result parser requires every exact

## Remaining boundaries

This repair removes four optional fields from relay publish envelopes. It does
not claim all SDK telemetry, initialization ordering, handshake metadata, IP
information or routing metadata is absent. The Events initialization/disable race
and stored-message collection while disabled require a separate controlled
review. They are an outstanding lead, not resolved by this encoder change.
The full wallet/dependency review and historical binary comparison remain open.
