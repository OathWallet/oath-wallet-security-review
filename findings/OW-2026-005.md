# OW-2026-005 — encrypted responses were correlated by ID without topic binding

> Current audit target: [5.0.2 (104) prerelease](../review/RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

Severity: **medium, protocol integrity and availability**.
Fix commit: `e352f56d0fb3be035c3600e646e3f9133adb9ef4`.
App Store availability is not established.

## Affected path and demonstrated impact

The baseline and `f506dd8b820476296a6348c0ccbbdc42164c21f5` use
`Vendor/Reown/Sources/WalletConnectNetworking/NetworkingInteractor.swift:363`
to resolve incoming responses by RPC ID through `RPCHistory.resolve`.
`Vendor/Reown/Sources/WalletConnectUtils/RPCHistory/RPCHistory.swift:81`
validates that an ID exists, then deletes its record without checking the
authenticated response topic or whether the request was locally originated.

With two synthetic encrypted topics, a response authenticated under topic B's
key and carrying a pending request ID from topic A was dispatched as a response
to that request. It also consumed A's pending record, so A's later legitimate
response was no longer delivered. Both success and error responses reproduced
this behavior. Correct-topic and duplicate-response controls also ran.

The sender in the reproduction knows B's key and the target request ID, but
not A's key. The test does not establish discovery of an unknown topic or ID,
production relay abuse/rate-limit behavior, a complete session takeover,
automatic signing, or fund theft. The default ID generator combines a millisecond
timestamp with a random value from 0 through 999; practical ID guessing was not
tested. The confirmed boundary failure is cross-connection response consumption.

## Repair and compatibility

Incoming relay responses now resolve history with an expected topic and require
a locally originated request. Rejected responses leave the pending record intact.
Ordinary requests expect their original topic. Protocols with a separate response
topic explicitly attach local routing metadata before sending; this metadata is
persisted in the history record but never encoded in or accepted from JSON-RPC.
Authentication and Notify request producers were updated to supply their actual
response topic.

Persisted records without the new optional field still decode. Ordinary legacy
requests retain their original topic. Legacy authentication requests derive the
protocol response topic from their already-stored requester public key using
SHA-256; malformed routing fails closed. The independent test vector hashes
32 bytes of `0x04` using Python hashlib. Stored wallet keys, wallet schemas,
Keychain identities and transaction wire formats were not changed.

The general-purpose Notify product is not linked by the app project. Its new
request producers supply explicit routing, but old pending Notify handshakes
without that metadata have no proven migration path; they may need to be retried.
No real Notify peer or end-to-end authentication peer was exercised. These
limitations are not presented as passing runtime compatibility checks.

## Reproducible evidence

`ResponseTopicAuthenticationTests.swift` is a four-case, legacy-API corpus that
can compile against the original SDK. `scripts/response-topic-check.py` exports
the exact f506dd8 SDK inputs, adds only that fixture, and runs them offline.
It exports the fixed inputs and runs the identical fixture again:

- Before: two adversarial cases fail; two legitimate-topic controls pass.
- After: all four pass, including keeping a rejected request pending and
  delivering the subsequent legitimate response only once.

`ResponseTopicCompatibilityTests.swift` adds eight checks for encrypted type-1
responses on a distinct expected topic (success and error), JSON routing-field
injection rejection, routing persistence across restart, legacy ordinary records,
legacy authentication routing, malformed legacy routing, and rejecting remote
requests as local responses. These exercise production history and decoding,
not copied routing logic.

```sh
python3 scripts/response-topic-check.py /path/to/oath-wallet --output /tmp/topic-evidence
python3 scripts/run.py /path/to/oath-wallet walletconnect-sdk
python3 scripts/run.py /path/to/oath-wallet walletconnect-verify
```

Exact source pins, fixture hashes, outcomes, durations and logs are retained in
the evidence records. A public source repair does not establish a completed
whole-wallet review or availability in an installed App Store build.
