# OW-2026-009 — Standalone EVM chain reply bypasses the client size limit

Severity: **informational**, a response-validation consistency and resource-hardening
defect. This does not demonstrate fund loss, signature substitution, secret
disclosure, a crashed app, or an exploitable denial of service.

## Root cause and affected path

At `2eef5a4912ce1680cd174c7596471620ffcf129e`,
`Packages/OathAnkr/Sources/OathAnkr/EVMSendClient.swift:46–56` sends a separate
`eth_chainId` request before broadcasting when that endpoint has not been
verified within 30 seconds. It checks HTTP status, JSON-RPC version, response
identifier and chain identity, but omits the 8,388,608-byte bound applied to
ordinary batch replies at line 67. Both paths decode untrusted provider data.

The default `AnkrHTTPTransport.raw` separately caps the received byte stream
at 64 MiB. Therefore this is **not unbounded network buffering**. It lets this
client decode and accept replies between its intended 8 MiB limit and the
transport's larger ceiling. Diagnostic parsing has a separate 1 MiB cap and
does not substitute for the missing client check.

The relevant trust boundary is a configured RPC provider's response. A local
fixture returns valid chain-check JSON padded with spaces to exactly 8 MiB +
one byte. Before repair the client accepts it and invokes the synthetic
broadcast handler. The test uses `0x00`, not a signed/fundable transaction;
network access is denied throughout execution. Accepting the oversized reply
does not bypass the independent signature and plan checks in `submit`.

## Before and after

Regression-only commit `04a239277b3b7a90ff5737b682cf2183bc5616fb` adds three
tests without changing production code. In each of three separate processes:

- The standalone over-limit rejection test fails both expected assertions:
  the response is accepted and a synthetic broadcast is admitted.
- The exactly-at-limit standalone control passes.
- The ordinary batch control accepts the exact limit and rejects one byte over.

Fix commit `6124254d43ee7a98d4a364639671ccfc52155396` applies the existing
client size limit before decoding the standalone reply. All three tests pass
in each of three separate processes after repair. Fixture bytes are identical
before and after. The runner rejects missing/duplicate selectors, skips,
crashes and unrelated assertion failures as reproduction evidence.

No authorization, transaction construction, persistence format, provider list
or default transport behavior changes. An oversized response follows the
existing malformed-response/fallback handling. The generic transport's 64 MiB
streaming ceiling remains unchanged; this repair limits client acceptance and
decoding, not the bytes already received by the transport.

The repair is merged in [public app PR 13](https://github.com/devdasx/oath-wallet/pull/13).
Merge `eb78da3e7690a1ad3eca6a1e0970882600ac19eb` has the identical source tree
as the tested repair commit. This is source equality, not App Store binary equivalence.
