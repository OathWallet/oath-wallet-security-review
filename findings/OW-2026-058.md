# OW-2026-058 — Revealed private keys survive into app-switcher snapshots

**Severity: medium.** A person who can view the app switcher on the unlocked
device may see a previously revealed private key without reopening the wallet's
lock. The value controls the associated account, but exploitation requires a
prior authorized reveal and local screen access. This is not a remote extraction
or an iOS device-lock bypass.

**Affected release:** 5.0.1 (103),
`c7acd23bb139864a40273f405d18b479589d2b20`. The same model remains present at
`e8e6ba9fb910a1ca31c60e0d8dac8ac84583091b`.

## Cause and source

- `OathAtmosphere/Wallet/OathPrivateKeyModel.swift:240–244` deliberately excludes
  the `revealed` phase from cancellation cleanup.
- `OathAtmosphere/Home/OathWalletSheets.swift:436–475` calls this cancellation
  method on lock and background. The revealed value therefore survives both.
- `OathAtmosphere/Home/OathPrivateKeyPages.swift:259–268` renders the retained
  value. Copy/QR authorization gates do not remove text already on the page.
- `OathApp/OathAtmosphereApp.swift:73–110` retains the home/sheet hierarchy and
  defers a new native lock presentation in the background.
- `OathApp/OathSceneDelegate.swift:276–289` attaches the optional privacy cover
  only when enabled. `OathAppSettings.swift` defaults that preference to false.

The optional cover is a separate user preference. Secret disclosure cleanup must
not depend on enabling it. Native Back to the warning while the session remains
active is a different operation and may preserve the same authorization.

## Reproduction and limits

An isolated iOS 27.0 simulator ran a synthetic fixture with the production scene,
root lock rules, private-key model and private-key display. Initial encrypted
wallet loading and home content were replaced with a fake profile and a presented
production disclosure page. The reader returned the deliberately invalid text
`AUDIT-SNAPSHOT-TEST-NOT-A-PRIVATE-KEY`; no real wallet credentials were used.
The fixture invokes the same cancellation callbacks as the settings owner.

After launching Settings to background the fixture, its lifecycle record shows
the session locked while the model still held the revealed value. Both actual
iOS-generated light/dark scene snapshot files contained the readable fixture
value. The original texture files, decoded PNGs, OCR output, source injection and
logs are retained. This goes beyond the earlier settled-blur experiment, which
explicitly attached a cover and did not test the disabled-cover case.

This is a bounded production-component integration experiment, not a complete
wallet creation/export UI run. It does not test a physical device, every OS,
every transition timing, or memory zeroization. It does not establish that an
arbitrary third-party app can read another app's snapshot files.

## Repair

[Public repair #71](https://github.com/devdasx/oath-wallet/pull/71),
`b5621109b64d606dcf6cd906d2c4f2c2f9e78686`, makes
`cancelAuthentication()` call the existing `returnToChains()` cleanup for every
phase. This clears visible and pending values, selection and browser state,
cancels in-flight work and invalidates its generation. Existing settings routing
returns to the public chain list. Reopening requires another authorization and
warning acknowledgement. No persistence format, wallet key, clipboard behavior
or general app-switcher preference changes.

With exactly this model patch in the same runtime fixture, both foreground
controls still contain the fake value, while all four resulting snapshot files
contain no recognized fixture value. Both scene snapshots were also inspected
visually. Lifecycle records show the value and revealed state cleared after lock.
The one isolated simulator was shut down and deleted after the check.

The fixture setup initially attempted an unavailable Intel aezeed simulator
slice, then incorrectly overrode all framework bundle identifiers. Both attempts
are preserved. The final setup builds arm64 and changes only the application
target's identifier. Neither setup error is an application vulnerability.

## Validation status

The identical 11 host cases on the previous production model produce **seven
passes and four failures**. They check active disclosure and native Back controls,
clearing on cancellation, refusal to reuse old acknowledgement, retained public
accounts, and fresh authorization. The repaired model passes **all eleven**.
The full host harness passes **791 checks**. Diagnostics pass **119 tests**, with
two explicit skips. Coverage, public source validation, a zero-match secret scan
and unsigned generic iOS Release compilation pass at the exact repair commit.
The merge commit is `00d26c005fbc3f811615b23b865bb50ef7b6619f`; its tree is identical
to the tested repair. No App Store delivery or installed-binary equivalence is claimed.
