# OW-2026-048 · Wallet insertion can trap on exhausted database counters

**Impact.** A wallet insert can terminate the process when an existing display number in the same group or the overall sort position equals the largest Swift integer. These are local availability defects affecting very unusual stored values. The name-index fixture reaches the boundary through the production database import API. The sorting fixture sets the extreme value explicitly in a temporary SQLite database. Neither fixture demonstrates a remote way to reach the condition.

**Reproduction.** In the [build 103 database implementation](https://github.com/devdasx/oath-wallet/blob/c7acd23bb139864a40273f405d18b479589d2b20/Packages/OathDatabase/Sources/OathDatabase/OathDatabase.swift#L130-L153) the writer adds one to a stored maximum before inserting a row. Each original test ran in its own process with networking denied. The two crash reports identify arithmetic overflow at lines 145 and 147 respectively. [Original fixture and crash evidence](../evidence/5.0.1-build103/sql-counters/original.json).

**Repair.** [Wallet PR 61](https://github.com/devdasx/oath-wallet/pull/61) retains the existing fast append path while a larger integer is available. When display numbers are exhausted, the writer finds the first free valid number within the group and preserves existing labels. A saturated sort order is compacted by the same sort, creation date and ID used to display the wallet list. Compaction and insert share a database transaction. An injected account conflict rolls both back. The repaired naming suite passed all seven tests, including subsequent allocation around occupied values and the failed-write rollback. The [replay](../scripts/wallet-number-limits.py) runs the crash fixtures and controls against their pinned commits.
