# OW-2026-014 — Router transfers omitted from the first approval summary

Severity: **medium**, an informed-consent/presentation defect. A decoded router
request can contain an ordinary swap plus a separate token transfer. The first
approval summary displayed the exchange while omitting the additional operation.
Full call details and a generic contract warning remained available. No signing
bypass, successful on-chain theft, malicious live dApp or funded transaction was
demonstrated. Transfer execution depends on contract state and existing permissions.

## Reachable source path and root cause

Regression-only baseline: `fe6d866751636da183a5de01b90c0f92ea4c5102`.
`OathWalletConnectSheet.message` passes the immutable EVM request into
`OathWCEVMReview.transactionReview`. When a router contains a swap, that view
uses `WalletConnectSwapReview` and suppresses the generic action fields.
`WalletConnectSwapReview.swift:23–95` retained routes and native conversions,
but not decoded transfer or balance-check steps. `OathWCSwapSummary` therefore
could not display them. Fully decoded extra operations did not trigger its
incomplete-decoding warning. Router requests without swaps also lacked the
ordered operations on this first screen. The separate expanded call-details
screen already displayed the commands; the bug was not absence from all screens.

The decoder recognizes command 0x02 as a Permit2 transfer. The upstream
[dispatcher at edf19bf](https://github.com/Uniswap/universal-router/blob/edf19bfde87e6cf5b29046f6ca2f483a4ffd6ae6/contracts/base/Dispatcher.sol#L102)
passes the message sender, mapped recipient and amount to `permit2TransferFrom`.
Commands 0x04/0x05 operate on router-held balances. This source comparison explains
why transfers differ from swap routes; it does not prove bytecode equivalence
for every deployment on the application's allowlist.

## Repair

Implementation: `3e553d55caf22a3dbed7baaa65473d2a8d5e109b`.
Final tested source: `e46fff5686db48a40103c9dbffe5e830cfc5548a`.
The production approval model now retains every decoded operation in order and
the deadline. The first approval screen uses the same command/value components
as expanded details, including token identity, exact or bounded amounts,
recipients, optional-operation warnings and unknown-operation warnings.
Transfer sources distinguish the signing account from router-held funds. Native
conversions remain visible even when also summarized by a compact swap route.
Standalone router transfers use the same display path. The request, signing,
fee validation, authorization and broadcast data are unchanged.

## Reproduction and limits

The same three-method Swift fixture and ten ABI vectors execute before and after.
The Python standard-library encoder is independently cross-checked with pinned
ethers 6.15.0. It verifies canonical ABI, nested input, token, amount, recipient,
payer and command semantics without RPC or keys.

Each Swift test runs in three fresh network-denied host processes. Before:
**30 specific assertion failures across six failed process executions**, plus
**three passing decoder/strict-boundary control executions**. After: **nine
passing process executions**. Different transfer amounts, recipients, command
order, nested optional commands and balance checks no longer collapse into an
identical approval model. The original fixture and vector hashes match between
phases. Missing, skipped, crashed or unrelated-failure tests are not accepted.
