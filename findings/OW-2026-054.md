# OW-2026-054 · Unchecked signature components can trap or accept malformed encodings

Severity is low within the current application scope. The public vendored signature type and the internal EIP191 verifier reproduce malformed-input crashes under direct host calls. The application references the type in its crypto adapter, but no application call into this verifier has been found. A remote app-entry-point exploit is unproven.

The serialized constructor slices short data and reads the last byte without validating the count. It also accepts non-65-byte data and unsupported recovery bytes. The raw constructor accepts arbitrary scalar lengths and recovery bytes, including values that overflow serialization. [Original signature type](https://github.com/devdasx/oath-wallet/blob/c7acd23bb139864a40273f405d18b479589d2b20/Vendor/Reown/Sources/WalletConnectSigner/Signer/EthereumSignature.swift#L8-L33).

Malformed input should produce an error before recovery or serialization. The repair validates component sizes, supported recovery identifiers and exact serialized length during construction. The EIP191 verifier propagates errors. Both constructors now throw, so source consumers must add `try`. Valid wire normalization and serialized bytes are retained.

The identical original and repaired fixtures cover empty and short input, wrong scalar sizes, every recovery-byte value and Data slices. Four isolated processes reproduce traps in the signature-type and verifier cases. The repaired cases pass.
