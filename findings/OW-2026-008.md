# OW-2026-008 — Queued refresh reads start during cancellation

> Current audit target: [5.0.2 (104) prerelease](../review/RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

Severity: **low** (cancellation/privacy and reliability boundary). Validation
and publication status are recorded in `findings/index.json` and the result
files; this finding does not demonstrate signing, secret disclosure or fund loss.

## Affected implementation and root cause

At application `27fcf5f58f6169e1a40fb6afced883bc736d124d`,
`Packages/OathDatabase/Sources/OathDatabase/AnkrSynchronizer.swift` lines 232–247
invalidated its epoch and then cancelled each worker separately. A cancelled
active request could release a shared `AnkrClient` permit before a queued
worker received its task-cancellation flag. That queued worker then began an
old refresh request while cancellation was still iterating the workers.

The client checked task cancellation, but there was no common request-admission
boundary for all workers in that refresh generation. The production client
and synchronizer at CI target `92423215ddd638b070c605a5911a9ebc7b15615f` have the
same source hashes as the affected implementation. The application adapter
`OathAtmosphere/Wallet/OathAnkrSync.swift:154` invokes this cancellation path;
`OathWalletSession.swift` invokes the adapter during session teardown.

These are balance/history queries containing public account identifiers.
Continuing queued queries after cancellation is unnecessary disclosure of
activity to the configured provider and wastes requests. No secret, signed
transaction or change to transaction authorization is involved. Existing
generation/database checks are separate protections; this reproduction does
not establish a stale-wallet write or a cross-wallet data exposure.

## Reproduction and retained history

The existing overlap/cancellation test failed in GitHub run
[41270221065, OathDatabase job](https://github.com/devdasx/oath-wallet-security-review/actions/runs/41270221065/job/124741593111):
eight requests instead of four after cancellation, and 26 instead of 22 after
a fresh refresh. That run targeted `92423215`, not the later fixed target.

Commit `70b86d4af234412aa8fe49a24935fcdb17aa4e2d` adds only a regression to
the affected `27fcf5f` implementation. Six synthetic chains queue three streams
each behind a four-permit client. A fixture transport releases a held request
from its cancellation handler and briefly holds the handler open. This exposes
the real worker-unwind/permit-admission interleaving without a live provider.
The required result is exactly four old requests, followed by 18 successful
fresh requests and 22 total. The same fixture is used before and after repair.

An initial exploratory fixture that paused only the first cancellation handler
passed once; that non-reproduction is retained, not represented as a baseline
failure. The final fixture pauses each cancellation handler up to 100 ms.
Its first run failed the admission assertion (seven instead of four), and
ten subsequent baseline process runs all reproduced the race.

`scripts/refresh-cancellation.py` builds each exact clean revision and repeats
the actual production-package test ten times in network-denied host processes.
Only failure of the named admission assertion counts as reproduction; crashes,
empty selections, wrong selectors, skips and unrelated failures are rejected.
Finite scheduler samples are not an exhaustive concurrency proof. The script
accepts baseline passes mixed with at least one specific race reproduction;
all ten repaired runs must pass. Logs retain the per-run outcomes and hashes.

The final clean-checkout, network-denied reproduction also failed in all ten
baseline runs and passed in all ten fixed runs. The fixture SHA-256 is identical
on both revisions. Build plus test durations were 374.013 seconds before and
366.459 seconds after; these include compilation and are not a performance
comparison. The first attempt to reuse an existing compiler cache failed before
any test: Clang saw the same module through `/tmp` and `/private/tmp` aliases.
Fresh canonical-path build directories resolved that tooling failure; both
attempts are retained. No production code was changed to suppress it.

## Repair

Commit `66e603301be904c6f9bfe0b3c0338fa704ffc1e2` introduces a monotonic,
lock-protected `AnkrRequestScope`. The synchronizer invalidates the old scope
before cancelling any workers and gives future refreshes a new scope.
Balance/history requests and the parallel whitelist inventory capture the
old scope. The client checks it before and after permit acquisition, before
retry admission, and after a transport response. Rejections release acquired
permits and do not retry. Existing callers can omit the optional scope.

Two additional production-client tests cover rejection before admission,
fresh-scope reuse, cancellation-resistant late responses, no retry, and
unrelated calls continuing normally. The original overlap/cancellation test
also remains in the full package suite.

This closes the reproduced queued-admission window. A request already admitted
before scope invalidation may already be in transit; cancellation cannot undo
a packet sent to a provider. This is not a claim of instantaneous network
revocation or proof of every other synchronizer's cancellation behavior.
Catalog fetching and database commit implementations remain separate review
boundaries. No storage format or wallet identity is changed.

## Validation correction discovered during the broad run

The first 1,404-case OathAnkr run on `66e60330` had 1,201 passes, 194 skips and
nine failures while several fresh compiler jobs were active. The same limits
and assertions on a second run produced 1,209 passes, 194 skips and one failure.
Both runs are retained. Eight non-reproductions on repeat are not proof of
universal scheduling stability.

The remaining TRON diagnostic test stopped waiting as soon as any `malformed`
event arrived, then asserted that a separately queued `tron_read` attempt event
was already present. The production recorder uses detached tasks, so those
records can arrive in either order. Commit
`2eef5a4912ce1680cd174c7596471620ffcf129e` changes only that test's wait predicate
to require both events. The same 30 iterations, 50 ms delay, correlation checks
and privacy assertions remain. No production diagnostic or wallet code changed.
This is a test synchronization repair, not an additional security vulnerability.
The corrected TRON case passes ten additional isolated, network-denied repeats.
Final validation uses this new commit; the earlier results remain labeled with
`66e60330`. Isolated build directories are explicitly reused for the final
checks; the earlier fresh build and exact production-input equality are separate
evidence, not a claim of a fresh final build.
