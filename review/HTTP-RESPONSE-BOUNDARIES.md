# Provider response boundaries in the unsigned iOS build

> Current audit target: [5.0.2 (104) prerelease](RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

A transport can enforce a byte budget at three points: before sending, while receiving, and before decoding. Only the middle check can prevent accumulation of an unexpectedly long unknown-length response. A size limit on an injectable decoder still matters for data that arrived through another path. The [finding and reproduction](../findings/OW-2026-034.md) describe the distinction.

## Paths examined

- **Bitcoin fee, broadcast and reconciliation.** The provider constructs the request according to network and API format. The signed broadcast bytes are sent in the HTTP body. Fee and broadcast responses have 65,536-byte limits. Raw/hex lookup limits are caller-specific. A known missing transaction can legitimately return empty. Admission, cancellation, provider cooldown, oversized and 404 classification and small policy errors were inspected together. Recovery from a failed broadcast still needs correlation against the originally signed transaction.
- **Raw Bitcoin parents and fee recovery.** The raw fallback takes at most 40 unique lowercase transaction hashes, bounds concurrent readers, applies a 4,000,000-byte maximum, and checks the hash of the parsed transaction before returning it. The fee fallback checks the chain bounds and units, tries its endpoints in order and stops on caller cancellation. Injected fetch closures still pass through decoder limits.
- **Exchange rates.** The transport accepts 200 and uses a 131,072-byte budget. Invalid rate data cannot be committed until date, USD base, numeric and minimum currency-count checks pass. Failure preserves the last provider cause through retry backoff. This checkpoint does not claim that a syntactically valid but dishonest price is independently authenticated.
- **Token metadata and app update checks.** Token lookup verifies its own request ID before interpreting a JSON-RPC result and preserves a non-200 status. The app version lookup checks HTTP success before interpreting the listing. Each default transport now caps the body at 1 MiB. Presentation, live providers and runtime service availability are separate.
- **Adjacent streaming clients.** The first-party market-data reader uses a 2,000,000-byte limit and rejects an excessive declared length. The Ankr balance transport counts actual bytes against 64 MiB. Contract identity uses 65,536 bytes and its caller verifies chain and address. Artwork validates approved destinations including redirects and checks its 8 MiB byte budget. None of those source observations establishes their peak-memory use or cancellation at each suspension point. The older general-purpose DiagnosticHTTP.data API remains available to library consumers.
- **WalletConnect.** The URLSession WebSocket adapter configures a 1 MiB message maximum. Binary delivery, relay routing, signature authorization, and previously documented journal findings have distinct boundaries. An HTTP response-size test cannot attest to those properties.

## Scope of the compiler-input index

Run `scripts/transport-inputs.py SOURCE DERIVED_DATA RELEASE_INPUTS_JSON OUTPUT_JSON` after generating the build ledger. It rehashes every selected compiler input and records network-related API spellings, source lines, and build targets. Treat each hit as a pointer. A synchronous URL read might read a local file, a wrapper named data might dispatch further, and a linked binary can use a transport outside all the scanned source files. Source selection is stronger than a repository search but does not prove a symbol was executed. The ledger intentionally grants no manual coverage for these matches.

For the two prebuilt dynamic Wallet Core products, the [artifact comparison](../evidence/provider-response/oath49-http-evidence/build-inputs/release-frameworks.json) compares the resolved arm64 iOS slice to the binary inside the built app. Both entire executable files were byte-identical, including their instruction sections. The inventory records all six Mach-O images' dynamic library references. Static archive members are a separate boundary and an independent build from upstream source remains outstanding.

## Independent BDK device-slice rebuild

We rebuilt the arm64 iOS static library from the publisher's BDK FFI source commit `1c5f4863c6a53cc9d063d34c4e13c91fea5c58de` using its Cargo lockfile, Rust 1.90.0, the release-smaller profile and an iOS 15 deployment target. The original publisher's runner was macOS 15.7.9. The [local toolchain record](../evidence/provider-response/oath49-http-evidence/bdk-device/toolchain.txt) identifies the compiler and SDK used for this reconstruction.

The published and rebuilt archive hashes were **different**. 525 member payloads were identical counting multiplicity, from 902 published and 902 rebuilt members. Of 906 published UniFFI entry-point names, 0 were missing and 0 extra names appeared in the rebuild. Of 857 published members containing instructions, 662 had matching instruction-section digests counting multiplicity. This comparison includes neither symbol relocation semantics nor the effect of linkage. The [package inventory](../evidence/provider-response/oath49-http-evidence/bdk-device/packages.json) records 156 packages that emitted compiler artifacts, distinguishing host build tools from target code, and verifies registry archive checksums against the lock. The comparison inventories each archive separately; equal symbol names establish interface overlap only. The source-to-binary equivalence gap is still open. The measurement does not identify a tampering event or explain each differing object.
