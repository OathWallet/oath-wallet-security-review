# Provider concurrency, Bitcoin recovery and Stellar source generation

> Current audit target: [5.0.2 (104) prerelease](RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

The review target remains `8c4e1d5d3a14bec0b9ea3a1fd01c7611ea4dd707`, descended from 4.1.15 (100). Results below identify later fixes separately.

## A waiting request could miss a completed result

The original GitHub job observed two underlying calls for one successful network-metadata request with only one slot available. The actor released its global and host permits before inserting the result. Either await allowed another queued task to observe an empty cache. The repair puts cache insertion before either suspension. All per-host and global limits and cancellation checks remain in use. See [OW-2026-043](../findings/OW-2026-043.md) and the [original failed job](https://github.com/devdasx/oath-wallet-security-review/actions/runs/41374244665/job/125179964004).

I read the full [provider file at the review pin](https://github.com/devdasx/oath-wallet/blob/8c4e1d5d3a14bec0b9ea3a1fd01c7611ea4dd707/Packages/OathAnkr/Sources/OathAnkr/PublicCheckProviders.swift). The endpoint constructor checks its caller-supplied string before building provider URLs. The cache admits six metadata methods, keys on URL and canonical JSON, and caps the number, size and lifetime of responses. Account and token lookups bypass this cache. The host-permit dictionary itself has no host-count bound. The built-in callers use a fixed set of hosts. The public app source search found instantiations of this specific transport in package tests only. The observation establishes extra work in the library; it does not establish a change to signed transactions or wallet balances.

## Bitcoin send and recovery

I traced [send-screen state](https://github.com/devdasx/oath-wallet/blob/8c4e1d5d3a14bec0b9ea3a1fd01c7611ea4dd707/OathAtmosphere/Send/OathBitcoinSendModel.swift) and the [send service](https://github.com/devdasx/oath-wallet/blob/8c4e1d5d3a14bec0b9ea3a1fd01c7611ea4dd707/OathAtmosphere/Send/OathBitcoinSendService.swift) through quotation, cancellation, wallet authentication, reservation, signing, persistence and retry. The screen captures wallet, recipient, amount, options and a generation for each quote. Leaving review cancels the task and invalidates late UI results. Signing separately verifies the saved plan, reserved input set, wallet identity and derived change address. The database validates the signed bytes and writes their history identity in a transaction before the service can broadcast. Failed submissions can return an unconfirmed ID without releasing signed inputs.

The recovery path deserves a separate adversarial test. It derives an ID from the stored payload, then its status reader matches input outpoints before consulting history. A test should independently vary the stored payment outputs, transaction identity and witness while keeping input outpoints constant. No altered transaction was submitted, and this checkpoint makes no claim of an exploitable transfer. These two files have partial dispositions until the resulting behavior and cancellation during reconciliation are tested.

## Stellar XDR generation

The Stellar SDK pin in the reviewed app is `b5dac0a6e8ff312d597c9a3b4269b03131d66e0d`. All 13 bundled XDR schema files matched the official [Stellar schema revision](https://github.com/stellar/stellar-xdr/tree/c40231c76bf2ebce76b24aa11c72508ac3eaa329). Starting from an empty output directory, Ruby 3.4.12, Bundler 2.7.2 and the [SDK generator](https://github.com/Soneso/stellar-ios-mac-sdk/tree/b5dac0a6e8ff312d597c9a3b4269b03131d66e0d/tools/xdr-generator) regenerated all 458 marked Swift files. The file set and every byte matched. The generation process was denied network access after installing the locked dependencies. The [reproduction workflow](../.github/workflows/stellar-xdr-generation.yml) specifies the commands, and the [digest manifest](../evidence/progress55/stellar-generation.json) identifies each file and schema.

All 458 files occur in the pinned Release compiler trace. Their ledger entries now record verified generation and preserve their earlier semantic-review status. Hand-maintained source, validation of the generator’s semantics, protocol correctness for adversarial XDR, and binary equivalence are separate work. [Updated compiler-input ledger](../evidence/progress55/compiled-inputs.json).

## Where the failed workflow stopped

The full GitHub run failed three jobs. All 84 downloaded archives matched GitHub’s SHA-256 digests. Within those archives, 98 passing records and one failing record had a matching source pin and a byte-verified log. Records and archive identifiers are in the [CI manifest](../evidence/progress55/ci-artifacts.json). The original job conclusions and failed logs remain part of the review.

In the extended-key job, an unrelated CJK two-factor test had changed the entire Electrum test file. This prevented the final-child comparison from starting. Both comparison builds now use the original test files and their original helpers. The compared production source remains pinned to its own revision, and the runner records both the compiled fixture hashes and the target checkout’s test-file hashes. The original comparison reproduced four boundary failures and passed one control. All five cases passed on the reviewed target. [Paired results](../evidence/progress55/local/child/utxo-child-boundary.json).

The separate Bitcoin input job failed during compilation, and the runner then lost DNS access when uploading its compiler log. The original compiler diagnostic was unavailable. Both pinned build-and-test phases completed locally. The earlier source accepted the two non-ASCII address variants and trapped on the sliced message fixture. The repaired source rejected those addresses, handled the slice and passed the byte-limit control. The harness now prints the compiler tail and propagates its exit code on failure. An injected compiler failure returned exit 37 with no passing result file.
