# From the private-key field to the BDK decoder

The public app trims input, checks the network choice, delegates UTXO input to that network's decoder, and holds the resulting scalar and extended-key data in its protected wallet model. It supports Bitcoin x/y/z versions, Litecoin-specific aliases and Dogecoin-specific versions; Bitcoin Cash uses Bitcoin version bytes. These inputs may share a scalar but a different chain code, depth or derivation path produces a different wallet.

We followed the original accepted encoding through the UniFFI DescriptorSecretKey constructor, miniscript's secret descriptor parser, rust-bitcoin's Xpriv decoder and secp256k1's scalar validator. The bridge's secret_bytes method derives the recorded path for a single extended key and returns an empty vector for wildcard/multipath cases. Its derive method appends the requested derivation to any path already present, updates the origin and preserves the wildcard type. These are distinct from verifying that data claimed to be a private key is encoded as one. Xpriv's encoder writes the zero byte; its decoder reads the scalar after that byte. The corresponding Xpub decoder passes the complete key field to the public-point parser. The app now checks the private/public marker against the version before invoking either decoder. [Finding and affected paths](../findings/OW-2026-035.md).

The recovery fixtures use an independent OpenSSL secp256k1 public point calculation and Python HMAC-SHA512 BIP32 derivation for the first legacy receive leaf on each chain. Re-encoding a stored malformed envelope must reproduce its exact committed script; exporting its private leaf must produce the same script again. Chain code, hierarchy, version, scalar and compression matter. Strict new imports, authorized access to pre-existing records, descriptor identity, leaf export and backup restoration are separate checks.

The code reviewed here is a slice of four upstream files, not full coverage of Rust key management or secp256k1 internals. Other constructor paths, rare derivation failures, FFI memory handling, formatting and zeroization, native implementation details, and independent binary equivalence remain open. The Rust crate inventory is tied to verified publisher-lock archive checksums; unreviewed entries remain visible.

## What the binary evidence establishes

The independent BDK archive build recorded 212 Cargo compiler artifacts. The [source trace](../evidence/typed-keys/oath50-release-evidence/provenance/rustc-inputs.json) resolved the dep-info file for each one, checked source hashes against the locked crate archives or bridge Git blobs, and attributed the inputs to the build host or the iOS target. It verified 2,512 distinct source files and hashed seven generated inputs. The bridge and four crate distributions were already inventoried. The [additional ledger](../scope/upstream-bdk-rust-selected.json) adds 2,348 previously untracked registry files. This traces the independent reconstruction. It does not prove which functions survived final linking. C/assembly sources compiled by Cargo build scripts, system libraries and toolchain internals need their own evidence.

Parsing Mach-O load commands reveals a concrete difference in the device slices: 274 published members recorded SDK 18.5 while 274 members of the local rebuild recorded SDK 27.0. Both used an iOS 15 minimum in those records. Among objects with the same name, one has a different SDK marker and an identical digest of its instruction sections. Metadata alone cannot explain differences in other instructions. [Archive metadata comparison](../evidence/typed-keys/oath50-release-evidence/provenance/sdk27-versions.json) · [Public hosted SDK 18.5 reproduction job](https://github.com/devdasx/oath-wallet-security-review/actions/runs/41361917821).

The [dynamic export check](../evidence/typed-keys/oath50-release-evidence/build-inputs/bdk-linked-exports.json) rehashed all six Mach-O images in the final unsigned app. Exactly the 906 published BDK UniFFI export names appear in OathBitcoin.framework. They appear in none of the five other images. This confirms where the interface is linked. It does not imply that all 906 entry points are called.

The [hosted reconstruction](../evidence/typed-keys/oath50-release-evidence/provenance/sdk18-5/identity.json) completed on macOS 15.8.2, Xcode 16.4 and SDK 18.5. All 906 FFI names matched. Exact archive-member payload matches rose to 788 of 902, and raw instruction-section digest matches to 856 of 857, counting multiplicity. The different runner, paths and SDK complicate attributing this improvement to a single variable. The [full archived comparisons](../evidence/typed-keys/oath50-release-evidence/provenance/sdk18-5/comparison.json) remain available after Actions artifacts expire.

The remaining instruction digest belongs to a UniFFI testing-library member compiled as part of the bridge feature graph. In the published object, AArch64 register w1 receives the immediate 70. The adjacent relocations reference the recorded 70-byte Cargo executable path and Rust Command::new in get_cargo_build_messages. The hosted toolchain's path is 146 bytes. Changing only that immediate in an in-memory copy of the published object reproduces the hosted member's complete instruction-section digest. [Offsets, paths and digests](../evidence/typed-keys/oath50-release-evidence/provenance/cargo-path.json). This does not reproduce the archive, its non-code data, relocations or signatures.

Replaying the actual OathBitcoin linker invocation, redirecting all outputs and requesting a map, reproduced all embedded instruction sections and the Mach-O UUID. The map selected 282 archive members and retained get_cargo_build_messages in its live symbol list. This establishes linker inclusion, not whether an app path calls that function. [Replay results and selected members](../evidence/typed-keys/oath50-release-evidence/build-inputs/bdk-linked-members.json).
