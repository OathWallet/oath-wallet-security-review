# Bitcoin Cash funding outputs and signing

> Current audit target: [5.0.2 (104) prerelease](RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

A token-bearing output can contain ordinary BCH value. Counting that BCH in a balance must not make the output available for a BCH-only payment. Oath parses the prefix to recover the locking script, verifies the previous transaction ID, amount and output index, and tests the original output bytes for the token marker. Both the database spendable-output projection and BitcoinSendCoin.validate exclude those outputs. BitcoinCashSendSigner and the multisignature signer call plan validation before requesting keys or signing. The multisignature path also rederives the script from the authenticated policy. ## Prefix reader

The parser bounds the optional commitment and amount against the original bytes before advancing. It requires canonical CompactSize integers, a positive signed-64-bit fungible amount, and defined token flag combinations. It can parse longer future commitments without marking the output spendable. This reader recovers the locking script and does not implement node consensus. The supplied valid and invalid JSON fixtures matched the complete bytes in the pinned upstream repository. The corpus covered all 256 flag values, every nonempty truncation of each valid prefix, amount and commitment boundaries, and 2,048 deterministic rounds of generated inputs. The production reader handled each input both as owned Data and a nonzero-based slice. It accepted 8,376 and rejected 14,584, with every accepted script compared byte-for-byte. [CashTokens specification](https://github.com/cashtokens/cashtokens/blob/41d2444c17bbfb456d4061953a3ed0e32161571b/readme.md) · [Runner](../scripts/cash-token-prefixes.py).

## Signing boundary

The ordinary BCH signer constructs ALL|FORKID preimages with each verified funding value and locking script. The multisignature signer constructs the redeem script, requires a valid threshold and distinct public keys, and verifies the funding script before signing. Both check signed inputs, outputs and serialized size against the reviewed plan. Bitcoin Cash Node 29.2.0 accepted and mined 20 ordinary payments, including one using 255 inputs. A separate chain rejected a missing fork-ID flag and a changed payment amount while accepting the original. On a third chain, 121 multisignature policies were funded and spent. These include every threshold for two through fifteen fixed keys, an HD policy and a mixed-key policy. Removing a signature failed each time. The 121 spend transaction IDs were read back from their mined blocks, with zero peers and P2P networking disabled throughout the checks.
