# The final normal child and the Swift curve boundary

> Current audit target: [5.0.2 (104) prerelease](RELEASE-5.0.2-104.md). Earlier results below retain their original tested versions and commits; they are not retroactively tests of build 104.

## Address ownership, export and spend

A BIP32 branch has 2³¹ normal child numbers. Child 2,147,483,647 is valid. In Swift a range that selects only that child has an *exclusive* end of 2,147,483,648. The original address API rejected that end. The change validator and the single-key, multisig and Electrum ownership checks also rejected the valid index itself. Oath now compares an actual index strictly below the first hardened child and permits a half-open range to end exactly there. The key export paths still derive the known branch and compare the complete selected address before returning the leaf. The fixed-key boundary still permits only its single address. This case concerns explicit derivation or recovery of an extreme index. Automatic gap discovery is separately bounded, and we found no evidence of lost funds. [BIP32 conventions](https://bips.dev/32/#extended-keys) · [Public repair](https://github.com/devdasx/oath-wallet/pull/49).

An independent oracle starts with the public byte sequence 00 through 1f, computes BIP32 HMAC-SHA512 and uses OpenSSL for secp256k1 compression. The four expected legacy P2PKH scripts correspond to the BIP44 coin types for Bitcoin, Bitcoin Cash, Dogecoin and Litecoin. The shipped code must reproduce each, export its WIF, and reproduce the same script when the WIF is imported. The host tests also use a synthetic previous transaction to exercise single-key and two-of-two multisig signing with the final child as input and change. A native SegWit Electrum leaf is checked against its exported public script. The negative control rejects both the first hardened child and a nonzero index on a fixed-key wallet. ## Seven operations at the curve library boundary

We read the complete Swift wrapper at the pinned revision. It creates and destroys a native context per operation. It requires 32-byte digests or scalar inputs where applicable. Secret input is copied into a temporary array in public-key creation, both signing paths and secret-key addition. Cleanup overwrites the temporary buffer on ordinary return or throw. The caller's original Data and compiler-generated copies have separate lifetimes. This source review does not establish erasure from all machine memory.

The DER signer randomizes its context, requests the library's default nonce function, serializes the result, and verifies it under the public key derived from the input. The compact signer also randomizes its context, then returns 64 scalar bytes plus a recovery ID. Recovery bounds the ID at 3, recovers an uncompressed point, and rejects a signature requiring high-S normalization. DER verification bounds encoded lengths and calls both native parsers before verifying. The public tweak operation parses the point before adding the tweak. The secret tweak operation checks the library's return status before returning the updated scalar. Each native operation maps errors to input-free Swift error cases. This disposition is limited to the Swift wrapper. Native field arithmetic, compiler behavior and side-channel resistance remain distinct review subjects. [Pinned Swift implementation](https://github.com/devdasx/oath-wallet/blob/7ecfa2c163704d363ebe6dc16b60151dc8a7cd78/Packages/OathSecp256k1/Sources/OathSecp256k1/OathSecp256k1.swift).

The independent fixture computes the RFC6979 nonce with Python HMAC, obtains its compressed public point from OpenSSL, and calculates the ECDSA scalars, low-S adjustment, recovery parity and DER bytes. The wallet must produce the expected DER and compact signatures, including on repeated signing, then verify/recover the expected public key. The same test corpus includes wrong digests, out-of-range secret keys and tweaks, point-at-infinity additions, high-S signatures, malformed DER, bad recovery IDs, invalid points and Data slices with nonzero start indices. The four XCTest processes run with network access denied. The original upstream library remains part of the shipped implementation; the fixture uses neither its nonce routine nor its signing or recovery functions to calculate the expected bytes. ## Reconstructing the native Bitcoin dependency

Both device builds ran with the same SDK 18.5 and Rust 1.90.0. Restoring the publisher's Cargo and checkout paths moved the comparison from 788 to 835 identical members out of 902. Every one of the 857 instruction-section digests matched. The member order and all raw section relocation records matched. In each of the 67 remaining objects, the comparison found differences in C strings, constant data, embedded LLVM bitcode, the header/load commands, and the symbol table. Replacing the toolchain's standard-library source prefix in the **original C string bytes** with the matching Rust compiler revision path reproduced all 67 full C-string section digests. This accounts for that section only. The raw archives still have different hashes.
